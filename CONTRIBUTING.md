# Contributing to ATLAS

**Everyone on this team can contribute anywhere.** You are not assigned to a module, and you do not
need permission to improve any part of this project — backend, ML, frontend, security, DevOps, UI/UX,
docs, or anything else you think would make it better.

👉 **[`docs/team/WORKFLOW.md`](docs/team/WORKFLOW.md)** has the exact commands: clone, branch, commit,
push, open a PR. Start there. This file covers the rules behind them.

## Before your first commit

```bash
pip install pre-commit && pre-commit install
```

**This is mandatory.** The hooks include a secret scanner. This repository is public and describes a
law-enforcement system; see [`PUBLIC_REPOSITORY_SECURITY_BOUNDARY.md`](PUBLIC_REPOSITORY_SECURITY_BOUNDARY.md).

## Non-negotiables

1. **Never commit real data or secrets.** If you commit one by accident, treat it as compromised and
   rotate it — rewriting history is not a remedy. Follow `docs/security/incident-response.md`.
2. **Never weaken a leakage gate to make a test pass.** The five gates in master spec §19 exist to stop
   us fooling ourselves. If a gate fires, it has found a real problem. Fix the problem.
3. **Never hand-write a metric.** Numbers come from `make eval`. If a number appears in a doc, a slide
   or a commit message, it must be traceable to a generated report and a git SHA.
4. **Never claim certainty.** Master spec §2 lists the required and forbidden vocabulary. It applies to
   code comments, log messages, UI strings and commit messages.
5. **Respect module boundaries.** `import-linter` runs in CI. If it blocks you, the fix is an interface,
   not an exception.
6. **Never commit real or sensitive data.** Development uses **synthetic data only**, generated by
   `simulator/`. No real PII, financial data, account numbers, complaint text or case material — this
   repository is public.

## Workflow

```bash
make verify        # run before every push: lint, types, boundaries, tests, secret scan
make test-leakage  # run after touching anything in features/ predict/ entity/ simulator/
make eval          # regenerate metrics after any model or data change
```

Branch from `main`, open a PR, get one approval, merge. **Nobody pushes directly to `main`, including
the maintainer.** Keep pull requests small enough to review properly. CI must be green.

Full command-by-command guide: [`docs/team/WORKFLOW.md`](docs/team/WORKFLOW.md).

## Commit messages

State what changed and why. If a change affects a reported metric, say so explicitly — a silent metric
change is the single most damaging thing that can happen to this project's credibility.

## Adding a dependency

Justify it in the pull request. Master spec §7: every major technology needs a documented architectural
reason. If it's significant, write an ADR.

## Changing a decision

Do not edit an accepted ADR. Write a new one that supersedes it and update `docs/adr/README.md`.

## Changing the label definition

This invalidates **every previously reported metric**. It requires an ADR, a version bump in
`docs/ml/label-definition.md`, and full regeneration of all reports. Do not do this casually.
