# Team Workflow

Everything a teammate needs, in the order they need it. If something here is wrong or unclear,
that's a bug — open a PR against this file.

**The one rule:** `main` always works. Everything else is negotiable.

---

## 1. One-time setup

```bash
git clone https://github.com/thesurajgupta/atlas.git
cd atlas
```

```bash
cp .env.example .env
```

`.env` is gitignored and must stay that way. It contains local development values only — never a real
credential, in any environment.

```bash
python3 -m venv .venv && .venv/bin/pip install --upgrade pip
.venv/bin/pip install pre-commit && .venv/bin/pre-commit install
```

**Installing pre-commit is not optional.** This repository is public. The hooks include a secret
scanner, and they are the last thing standing between a mistake and a permanently published credential.

```bash
make up          # PostgreSQL + PostGIS + H3 + TimescaleDB, and Redis
make verify      # should print "verify passed"
```

If `make verify` fails on a clean clone, that is a bug in the repo, not in your machine. Open an issue.

## 2. The everyday loop

```bash
git switch main && git pull
```

```bash
git switch -c feat/short-description
```

Branch naming — the prefix tells reviewers what kind of review it needs:

| Prefix | For |
|---|---|
| `feat/` | New functionality |
| `fix/` | Bug fix |
| `ml/` | Model, features, evaluation |
| `docs/` | Documentation |
| `infra/` | CI, Docker, tooling |
| `sec/` | Security |
| `refactor/` | No behaviour change |

Then work, and commit as you go:

```bash
git add -A && git commit -m "feat(predict): add Hawkes baseline for Tier 1"
```

Before you push:

```bash
make verify
```

Push and open the PR:

```bash
git push -u origin feat/short-description
```

```bash
gh pr create --fill --base main
```

No `gh`? Push, then open the link GitHub prints in the terminal output.

## 3. While your PR is open

- CI runs automatically. It must be green.
- One approval from any teammate is required. **Any teammate — not a specific one.**
- A reviewer is auto-requested based on `CODEOWNERS`. That is a hint about who has context, **not** a
  restriction on who may approve.
- Address comments with more commits. Don't force-push once review has started — it makes the
  reviewer re-read everything.

Keeping up to date with main:

```bash
git switch main && git pull && git switch - && git merge main
```

Use `merge`, not `rebase`, on a branch someone else may have pulled.

## 4. Where to contribute

**Anywhere.** You are not assigned to a module and you don't need permission to touch one.

If you're not sure what to pick up:

```bash
gh issue list --label "good first issue"
```

```bash
gh issue list --label "help wanted"
```

Reading the [master specification](../ATLAS_MASTER_SPEC.md) is the fastest way to find something worth
doing. §50 lists the acceptance criteria — anything unmet there is fair game.

Some areas reward care rather than caution. Sensitive paths (auth, audit, `atlas.intel`, leakage gates,
evaluation, the spec and ADRs) are listed at the bottom of `CODEOWNERS`. You may absolutely change
them — please just wait for the listed reviewer rather than merging on the first approval, because the
failure modes there are quiet.

## 5. Rules that are not negotiable

These exist because breaking them is hard to detect and expensive to undo.

**Never commit a secret.** No API keys, tokens, passwords, private certificates. The repo is public;
assume anything pushed was cloned within minutes. If you do commit one: **rotate it first**, then tell
the team. Rewriting history does not un-publish it.

**Never commit real data.** No real PII, real financial data, real account numbers, real complaint text,
real case material. Development uses **synthetic data only**, generated by `simulator/`.

**Never weaken a leakage gate to make a build pass.** The five gates in spec §19 exist to stop us
fooling ourselves. If one fires, it has found something real. Fix the cause.

**Never hand-write a metric.** Every number comes from `make eval`, stamped with a git SHA. If a number
appears in a PR, a doc or a slide, it must be traceable to a generated report.

**Never claim certainty the system doesn't have.** Spec §2 lists the required and forbidden vocabulary.
It applies to code comments, log messages, UI strings, commit messages and the pitch.

## 6. Commit messages

`type(scope): what changed`

```
feat(predict): add discrete-time hazard model for predicted window
fix(graph): stop trail traversal from crossing timestamps backwards
ml(eval): report PAI with bootstrap confidence intervals
docs(adr): supersede ADR-003 with Kafka migration trigger
```

If a change affects a reported metric, **say so explicitly in the message**. A silent metric change is
the single most damaging thing that can happen to this project's credibility.

---

## 7. When you're stuck

- Architecture question → [master spec](../ATLAS_MASTER_SPEC.md), then [ADRs](../adr/)
- "Why was it built this way?" → the ADR for that decision; every one lists alternatives considered
- "What does the problem statement actually require?" → [the verbatim text](../problem-statement/SIH26184-official.md). Never work from a paraphrase.
- "What still needs building?" → spec §50, and the [traceability matrix](../problem-statement/requirements-traceability.md)

Opening a draft PR early to ask "am I going the right way?" is encouraged and costs nothing.
